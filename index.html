What it does

Pulls independent NFL feeds into one internal model of games, players, injuries, and weather, then serves an activation-gated React client: weekly board, injury intelligence, settings, and simulated friends-leaderboard surfaces.

Data pipeline

Provider adapters normalize ESPN, NWS, and nflverse records with freshness and confidence metadata. Interval polling caches live feeds faster than historical backfills. Conflicts keep provider provenance instead of being overwritten.

Modeling foundation

Play-by-play for the most recent three NFL seasons drives team and player metrics (EPA, success-rate windows, opponent-adjusted rankings). Features respect a cutoff timestamp so future games cannot leak into training.

Security model

Username plus activation key; the backend redeems hashed keys and issues a signed session. STANDARD licenses expire on server time. Secrets stay off the frontend. Simulated money only — no real wagering.

Read the full technical breakdown

Platform architecture. FastAPI + SQLAlchemy on the server, React / TypeScript / Vite on the client. SQLite in development, PostgreSQL-ready for production. Replaceable provider interfaces cover sports data, odds, injury, weather, historical PBP, and news so one source can be swapped without rewriting the boards.

Fusion and injury intelligence. Name variants resolve to one internal player/team/game ID. Injury status transitions (for example QUESTIONABLE to OUT) are recorded as events for later recalculation. Outdoor venues get NWS weather; indoor games are skipped.

What stays private. The production prediction engine is server-side. This public repo is documentation for hiring review. Model weights, owner keys, and user history are not published.

1. Ingest Free providers land in adapters with timestamps, freshness, and canonical IDs.
2. Normalize Source records write into a shared database instead of each board scraping a different API.
3. Feature Recent-season PBP becomes team/player metrics with an explicit no-future-leakage cutoff.
4. Serve Activation-gated JSON APIs feed the weekly board, injury center, and simulated leaderboard.

What it does

WMMods

Dual-platform automation suite I designed, shipped, and maintain — a Windows desktop app and an Android companion that use OCR, calibrated screen regions, and rule-based decision logic to automate repetitive farming workflows, with GitHub Actions CI/CD and in-app auto-updates on both platforms.

What it does

Calibrates screen regions for battle UI, opponent name, HP bar, battle text, and shiny markers. Each encounter is captured, interpreted, and acted on automatically on PC (mouse/keyboard) or phone (Accessibility gestures + overlay controls).

OCR pipeline

Uses RapidOCR on desktop and Accessibility screenshots on Android to read opponent names and battle messages. Fuzzy species matching with guardrails reduces false positives from visually similar names.

Decision engine

Rule-based state machine: shiny override, target match, flee vs catch path, False Swipe until HP threshold (pixel-based bar analysis), Poké Ball loop with breakout retry, and separate modes that never run at the same time.

Release automation

Two repos with parallel pipelines: Windows PyInstaller builds and Android Gradle builds publish latest.json + binaries. In-app updaters poll GitHub Releases and install updates without manual file sharing.

Read the full technical breakdown

Platform architecture. WMMods ships as two products sharing the same product logic but different input stacks. The desktop build is Python with a mod-menu GUI, hotkeys, and PyInstaller packaging. The Android build is Kotlin with Jetpack Compose, an Accessibility Service for capture and taps, and a floating overlay for start/pause/stop while the game stays foregrounded.

Computer vision workflow. Users calibrate regions once; the bot clips those areas each loop. OCR extracts text from name and message regions. HP is estimated separately through color sampling on the HP bar (not OCR), because pixel thresholds are more reliable for progress detection than reading numbers from noisy UI art.

Decision logic. On each encounter the engine evaluates: Is the opponent a configured target species? Is a shiny marker present? Should grind mode KO instead of flee? If catch-eligible, the bot chains False Swipe until HP drops below threshold, switches to Poké Balls, and retries if the ball breaks out. Battle messages confirm caught/fled states before the next loop. Modes like farm automation, PvP helper OCR, and auto-entry are isolated so behavior stays predictable.

1. CI on push GitHub Actions builds on every push to main — Windows runner for the desktop exe, Ubuntu runner for the APK.
2. CD on tag Pushing a version tag creates a GitHub Release with the exact asset names existing updaters expect.
3. In-app update Each client checks Releases, compares versionCode/versionName from latest.json, downloads, and applies the update.
4. Stable repos Repo names stay fixed so friends' auto-update configs keep working across releases.

Why this project matters for my portfolio. It combines automation engineering, computer vision, cross-platform product design, and cloud-style release pipelines — the same skills I talk about in cloud and intelligent systems work, backed by repos and shipped artifacts instead of placeholder text.

WMNavigation

Windows Tarkov raid companion I designed, shipped, and keep live — a click-through overlay that tracks you on the map between screenshots, prices hovered items from the in-game name tooltip, and routes quests and loot, with GitHub Actions CI/CD and an in-app updater.

What it does

Localizes the player from in-raid screenshots, keeps the map marker walking between pings from movement keys, shows gunshot direction from game audio, and prices stash/raid items by reading Tarkov’s hover name box then looking up flea and trader value.

Name-tooltip pipeline

Crops a tight region above and to the right of the cursor — the same place Tarkov always draws the black name chip. Finds the gray-bordered box, OCRs the single white line, and matches it against the item catalog instead of guessing from the icon picture.

Live tracking

Screenshot localization is ground truth. Between V pings, WASD/sprint dead-reckoning slides the marker, optical flow updates look when capture works, and a compass HUD stays aligned to the current map north.

Release automation

Every user-facing change is smoke-tested, tagged, and published by GitHub Actions. The packaged exe checks latest.json on GitHub Releases and updates in place — same release pattern as WMMods, different product.

Read the full technical breakdown

Product architecture. WMNavigation is a Python / PySide6 desktop overlay. It never injects into Tarkov. Capture is in-memory BitBlt of the game window, input is global hotkeys plus async key state, and HUDs are click-through layered windows so Tarkov stays focused.

Computer vision workflow. A V screenshot is localized on the current map. Hover loot value waits for the stash name tooltip, OCRs it with Windows.Media.Ocr, and resolves price from the existing item catalog. Cached item icons remain a fallback if the name chip is not up yet.

Prediction and audio. With AI Prediction on, walk/sprint/strafe keys integrate along facing so the marker does not freeze between pings. A separate WASAPI loopback listener classifies gunshots and plots direction on the compass without rerouting game audio.

1. Smoke first python scripts/smoke_test.py must print SMOKE OK before a version is tagged — the same gate GitHub Actions runs.
2. CD on tag Tag v0.6.x builds WMNavigation.exe on windows-latest and attaches it to a GitHub Release with latest.json.
3. In-app update Installed copies poll Releases, compare versions, download the new exe, and relaunch.
4. Stable repo mikejschartner/WMNavigation stays the public source and download channel.

Why this project matters for my portfolio. It is a shipped Windows product with computer vision, overlay UX, and the same CI/CD discipline as WMMods — localization, OCR, real-time prediction, and automated releases instead of a demo script.
