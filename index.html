WMFarming

What it does

Calibrates screen regions for battle UI, opponent name, HP bar, battle text, and shiny markers. Each encounter is captured, interpreted, and acted on automatically on PC (mouse/keyboard) or phone (Accessibility gestures + overlay controls).

OCR pipeline

Uses RapidOCR on desktop and Accessibility screenshots on Android to read opponent names and battle messages. Fuzzy species matching with guardrails reduces false positives from visually similar names.

Decision engine

Rule-based state machine: shiny override, target match, flee vs catch path, False Swipe until HP threshold (pixel-based bar analysis), Poké Ball loop with breakout retry, and separate modes that never run at the same time.

Release automation

Two repos with parallel pipelines: Windows PyInstaller builds and Android Gradle builds publish latest.json + binaries. In-app updaters poll GitHub Releases and install updates without manual file sharing.

Read the full technical breakdown

Platform architecture. WMFarming ships as two products sharing the same product logic but different input stacks. The desktop build is Python with a mod-menu GUI, hotkeys, and PyInstaller packaging. The Android build is Kotlin with Jetpack Compose, an Accessibility Service for capture and taps, and a floating overlay for start/pause/stop while the game stays foregrounded.

Computer vision workflow. Users calibrate regions once; the bot clips those areas each loop. OCR extracts text from name and message regions. HP is estimated separately through color sampling on the HP bar (not OCR), because pixel thresholds are more reliable for progress detection than reading numbers from noisy UI art.

Decision logic. On each encounter the engine evaluates: Is the opponent a configured target species? Is a shiny marker present? Should grind mode KO instead of flee? If catch-eligible, the bot chains False Swipe until HP drops below threshold, switches to Poké Balls, and retries if the ball breaks out. Battle messages confirm caught/fled states before the next loop. Modes like farm automation, PvP helper OCR, and auto-entry are isolated so behavior stays predictable.

1. CI on push GitHub Actions builds on every push to main — Windows runner for the desktop exe, Ubuntu runner for the APK.
2. CD on tag Pushing a version tag creates a GitHub Release with the exact asset names existing updaters expect.
3. In-app update Each client checks Releases, compares versionCode/versionName from latest.json, downloads, and applies the update.
4. Stable repos Repo names stay fixed so friends' auto-update configs keep working across releases.
